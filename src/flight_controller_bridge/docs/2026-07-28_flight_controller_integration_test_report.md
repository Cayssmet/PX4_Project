# 树莓派—飞控完整导航链路联合测试报告

测试日期：2026-07-28  
报告用途：提交给飞控端开发 AI，协助核对串口协议、ACK、高度完成反馈和飞控安全门逻辑。

## 1. 结论摘要

本次已经在电机开关关闭的条件下，完成了真实雷达、树莓派导航程序、USB 转 TTL、飞控串口2和飞控 XCOM 调试输出的联合测试。

已确认以下端到端链路能够工作：

```text
N10 雷达
  -> ROS 2 /scan
  -> Cartographer
  -> map 当前位姿
  -> 航点管理器
  -> 水平位置/yaw PID
  -> flight_controller_bridge
  -> USB 转 TTL / 飞控串口2
  -> 飞控解析
  -> 飞控 XCOM 可观察到树莓派数据
```

反向状态链路也已确认：

```text
飞控状态 flags + ack_sequence
  -> 飞控串口2
  -> USB 转 TTL
  -> flight_controller_bridge
  -> /flight/status
  -> 航点管理器
```

因此当前可以判定为：**无电机台架条件下，完整导航命令链路和飞控状态返回链路已经跑通。**

本次不能判定为已经通过实飞验收，原因是电机开关始终关闭，未验证电机响应、真实闭环运动、完整航点切换和真实降落。

目前最需要飞控端协助确认的两项是：

1. 返回状态帧的 `ack_sequence` 有较多过旧或异常值，树莓派累计拒绝了 2584 帧；
2. 树莓派曾收到 `height_reached=true`，但保存的 XCOM 日志中 `HR` 始终为 0，需要确认 XCOM 变量和状态帧 bit0 是否来自同一状态。

## 3. 当前串口协议关键约定

树莓派以 50 Hz 发送固定 16 字节命令帧：

```text
AA 55 | sequence | flags | vx | vy | yaw_rate | target_height | CRC16 | 0D 0A
```

- `vx`、`vy`：`int16`，单位 mm/s；
- `yaw_rate`：`int16`，单位 mrad/s；
- `target_height`：`uint16`，单位 mm；
- `flags.bit0`：`control_valid`；
- `flags.bit1`：`land_request`；
- `sequence`：`uint8`，每个实际发送帧加1，自然回绕。

飞控返回固定 8 字节状态帧：

```text
55 AA | ack_sequence | flags | CRC16 | 0D 0A
```

- `flags.bit0`：`height_reached`；
- `flags.bit1`：`land_accepted`；
- `flags.bit2`：`land_completed`；
- `flags.bit3`：`failsafe`。

树莓派只接受落后最新发送序号不超过10帧的 ACK。50 Hz 下10帧约为200 ms。连续300 ms没有新鲜、CRC正确且ACK序号合法的状态帧时，树莓派将 `/flight/status.communication_ok` 置为 false，并阻止普通非零控制。

## 4. 多轮联合测试过程与结果

### 4.1 第一轮：真实串口和遥控器关闭状态

测试目的：确认 USB 转 TTL、飞控串口2、命令帧和状态帧能够双向通信。

结果：

- 树莓派成功打开 `/dev/ttyUSB0`；
- 首帧发送后很快收到合法飞控反馈；
- 未启动航线时，树莓派持续发送 `control_valid=false` 和零速度；
- 遥控器未开启时，飞控状态中的 `failsafe=true`；
- 开启遥控器后，`failsafe` 能恢复为 false；
- 说明物理串口、CRC、状态帧解析以及 failsafe 返回链路均已工作。

代表性树莓派日志：

```text
飞控串口已连接：/dev/ttyUSB0
串口=已连接，反馈=无/过期，安全门=任务状态缺失或过期；
发送 vx=0.000, vy=0.000, yaw_rate=0.000, valid=false；TX=1 RX=0

约1秒后：
串口=已连接，反馈=正常，安全门=任务状态缺失或过期；
发送 vx=0.000, vy=0.000, yaw_rate=0.000, valid=false；TX=52 RX=50
```

### 4.2 第二轮：遥控模式和程控切换

测试目的：按照实际操作顺序验证飞控授权和树莓派程控数据链路。

实际操作：

1. 开启遥控器；
2. 切到定点；
3. 等待约20秒；
4. 切到程控；
5. 电机开关保持关闭。

结果：

- 飞控反馈持续正常，`communication_ok=true`；
- 切换后树莓派安全门可以进入“普通控制有效”；
- 操作者在 XCOM 中确认飞控能够收到树莓派发送的速度数据；
- 定点/定高与程控/手控是两组独立选择，不能通过 `failsafe` 推断当前处于程控还是手控；
- 当前8字节状态帧没有单独返回“程控已授权”状态，因此树莓派只能依据反馈新鲜度和 `failsafe` 判断通信安全，不能直接确认飞控当前程控开关位置。

### 4.3 第三轮：雷达到飞控的完整正常流程

启动的功能包括：

- N10 雷达驱动；
- Cartographer；
- 地图坐标发布节点；
- 水平位置/yaw PID；
- 默认本地航线管理器；
- 飞控串口桥接节点。

默认本地航线为：

```text
route_id=1
航点1：(x=0, y=0, yaw=0, 高度=1.0m)
航点2：(x=1, y=0, yaw=0, 高度=1.0m)
航点3：(x=1, y=1, yaw=pi/2, 高度=1.0m)
```

由于机体连接多根线缆，只能由操作者手持小范围移动，因此没有完成整条航线，也不能把“未到达航点”解释为系统故障。

完整流程进入有效控制后的代表性日志：

```text
串口=已连接，反馈=正常，安全门=普通控制有效；
发送 vx=-0.003 m/s, vy=0.216 m/s, yaw_rate=0.000 rad/s,
高度=1.000 m, valid=true, land=false
```

手持移动过程中，定位和PID产生了连续变化的控制量。例如：

```text
发送 vx=-0.332 m/s, vy=0.248 m/s,
yaw_rate=0.769 rad/s, 高度=1.000 m, valid=true

发送 vx=-0.320 m/s, vy=0.192 m/s,
yaw_rate=0.800 rad/s, 高度=1.000 m, valid=true
```

这证明 `定位 -> PID -> 桥接 -> 串口` 的数据变化确实传到了飞控接口。由于测试中机体由人手持移动，上述位姿变化不能单独用来评价定位漂移；后续必须在机体完全静止和环境静止的条件下重新测量定位稳定性。

### 4.4 安全撤销测试

关闭流程中先停止航点管理器，使任务状态过期，再关闭PID、定位、SLAM、雷达和串口桥。

航点管理器停止后，桥接节点自动进入安全状态：

```text
串口=已连接，反馈=正常，安全门=任务状态缺失或过期；
发送 vx=0.000 m/s, vy=0.000 m/s, yaw_rate=0.000 rad/s,
高度=1.000 m, valid=false, land=false
```

该状态持续到串口桥被关闭。最终确认 ROS 2 节点全部退出，`/dev/ttyUSB0` 和 `/dev/ttyACM0` 均已释放。

这验证了树莓派侧在任务数据丢失时会撤销 `control_valid` 并发送安全零速度。

## 5. XCOM 高度和执行量日志分析

飞控 XCOM 保存的主要格式为：

```text
RPI_H C=93 T=100 AGE=0 HF=1 HR=0 LA=0 LC=0 FS=0
RPI_EXEC X=0cm/s Y=0cm/s Z=0cm/s YAW=0deg/s
```

按当前字段名称推断：

| 字段 | 推断含义 | 本次观察 |
|---|---|---|
| `C` | 当前高度，cm | 5～94，随手持升降变化 |
| `T` | 目标高度，cm | 始终为100，与树莓派发送1.000 m一致 |
| `AGE` | 最近树莓派命令年龄 | 始终为0，表示命令持续更新；具体单位需飞控端确认 |
| `HF` | 高度数据/高度控制有效标志 | 始终为1；精确定义需飞控端确认 |
| `HR` | 高度到达 | 保存片段中始终为0 |
| `LA` | 降落已接受 | 始终为0 |
| `LC` | 降落已完成 | 始终为0 |
| `FS` | failsafe | 前段为0，后段变为1 |

高度变化的压缩记录为：

```text
C: 90, 90, 82, 11, 11, 16,
   93, 93, 93, 94, 93, 93, 94, 94, 94, 93,
   13, 15, 12, 12, 11, 12, 12,
   5, 5, ...
T: 始终100
HF: 始终1
HR/LA/LC: 始终0
FS: 末段由0变1
```

该变化与操作者把机体举高、降低并最终放低基本吻合。当前没有证据表明水平N10雷达导致了飞控高度变化。

当 `C=93～94 cm`、`T=100 cm` 时，误差为6～7 cm，但 XCOM 的 `HR=0`：

- 如果飞控高度进入容差是 ±5 cm，这是合理结果；
- 如果设计容差是 ±10 cm，则需要检查连续确认时间、滞回逻辑或 `HR` 更新条件。

保存的 XCOM 片段中，全部 `RPI_EXEC` 都为零。可能原因包括：

- 该片段主要覆盖了树莓派撤销任务后的安全零输出；
- 电机开关关闭后，飞控安全门把最终执行量清零；
- `RPI_EXEC` 打印的是安全处理后的执行量，而不是串口刚解析出的原始命令。

操作者在实际测试中另外观察到过速度数据，树莓派日志也明确记录了非零发送值。因此建议飞控端同时打印两组值：

```text
RPI_RX   RAW_X=... RAW_Y=... RAW_YAW=... RAW_H=... VALID=... LAND=...
RPI_EXEC X=...     Y=...     YAW=...     Z/HEIGHT=... GATE_REASON=...
```

这样可以明确区分“串口是否收到”和“飞控是否允许执行”。

## 6. 高度完成反馈的不一致

树莓派航点管理器在同一轮运行中观察到如下变化：

```text
PID到达=false，高度到达=false，通信=true
PID到达=false，高度到达=true， 通信=true
PID到达=false，高度到达=false，通信=true
PID到达=false，高度到达=true， 通信=true
```

其中 `height_reached=true` 曾连续保持十几秒，之后又恢复为 false。航点没有推进，是因为水平/yaw PID到达和高度到达没有稳定地同时成立；结合手持移动和有限移动范围，这是预期现象，不代表航点逻辑断路。

但是，保存的 XCOM 文本中 `HR` 始终为0。树莓派桥接代码没有自行计算或锁存 `height_reached`，而是直接将飞控状态帧 `flags.bit0` 发布为 `/flight/status.height_reached`。因此需要飞控端确认：

1. XCOM 打印的 `HR` 是否与状态帧 bit0 使用同一个变量；
2. XCOM 日志与树莓派记录是否覆盖同一时间段；
3. 状态帧发送队列中是否积压了带旧 flags 的历史帧；
4. `HR` 是否可能短暂变化，而 XCOM 低频打印未捕获；
5. 飞控本地 z PID 的进入容差、退出容差和连续确认时间分别是多少。

此外，当前树莓派协议文档仍写着“第一阶段飞控固定发送 `height_reached=0`”，但真实测试中树莓派已经收到过 true。协议文档和飞控现状需要同步更新。

## 7. ACK 拒绝问题

### 7.1 现象

最后一轮桥接节点结束前的累计统计为：

```text
TX=31867
RX=32887
ACK拒绝=2584
反馈=正常
```

这里：

- `TX` 是树莓派成功写出的命令帧数；
- `RX` 是CRC、帧头、帧尾和ACK窗口均通过的状态帧数；
- `ACK拒绝` 是CRC等格式已经通过，但 `ack_sequence` 不在最近10帧窗口内的状态帧数。

按 `RX + ACK拒绝` 计算，约7.3%的已成功解析状态帧因ACK序号异常被丢弃。计数从桥接节点启动开始累计，包含启动后尚未执行航线的空闲阶段，不表示2584条控制命令发送失败。

拒绝计数呈现成批增加，而不是每帧稳定增加。例如本轮中出现过：

```text
ACK拒绝=2050
ACK拒绝=2327
ACK拒绝=2348
ACK拒绝=2420
ACK拒绝=2541
ACK拒绝=2584
```

整个测试期间仍不断收到新鲜合法状态，所以 `communication_ok` 保持 true，未触发控制中断。但如果连续300 ms都只有被拒绝的状态帧，树莓派会认为飞控反馈失联并撤销普通控制。

### 7.2 含义

ACK拒绝不是“飞控拒绝了树莓派命令”，而是“树莓派拒绝采用飞控返回的某些状态帧”。

假设树莓派最新发送序号为110：

```text
ACK=110：接受
ACK=100：接受，刚好落后10帧
ACK=99：拒绝，落后超过10帧
ACK=111：拒绝，属于未来序号
```

序号按 `uint8` 自然回绕，树莓派侧已经处理 `255 -> 0` 的正常回绕。

### 7.3 飞控端重点检查

1. `ack_sequence` 必须直接取“最近一帧通过CRC检查并已采纳的树莓派命令序号”；
2. 不要使用飞控自己的状态发送计数器作为 `ack_sequence`；
3. 检查 UART2 TX 队列是否积压旧状态帧；队列拥塞时应优先发送最新状态，不应长期发送历史状态；
4. 检查是否在多个任务、中断或DMA回调中并发修改 ACK 或 flags；
5. 检查序号变量是否为 `uint8_t`，避免有符号比较或回绕错误；
6. 串口重连或解析器重新同步后，不要继续发送上一次会话残留的状态帧；
7. 确保 XCOM 文本调试输出没有混入树莓派使用的 UART2 二进制协议通道；
8. 状态帧可以按固定频率发送，也可以收到命令后立即回复，但每帧都应携带发送时刻的最新ACK和最新flags。

下一轮建议增加以下调试行：

```text
RPI_LINK RX_SEQ=<最近合法命令序号>
         ACK_SEQ=<本次状态帧实际写入序号>
         FLAGS=<本次状态帧flags原始十六进制>
         RX_AGE_MS=<最近合法命令年龄>
         UART2_TX_QUEUE=<待发送字节数或帧数>
```

如果条件允许，树莓派端下一步也可以只在拒绝发生时打印：

```text
LAST_SENT_SEQ=<n> RECEIVED_ACK=<n> LAG=<n>
```

不建议直接增大树莓派的10帧ACK窗口来掩盖问题，因为这会降低对旧会话和串口积压数据的识别能力。

## 8. failsafe、程控授权与实际执行

测试确认：

- 遥控器关闭时，飞控可以返回 `failsafe=true`；
- 遥控器开启后可以恢复 `failsafe=false`；
- 树莓派撤销任务时会发送 `control_valid=false` 和零速度；
- 飞控端仍必须独立执行200 ms命令看门狗和遥控接管规则。

需要特别区分：

- `failsafe=false` 只表示飞控没有报告故障保护；
- 它不表示当前一定处于程控模式；
- 定点/定高与程控/手控是两组独立模式；
- 当前状态协议没有返回“程控已授权”或“电机开关已开启”。

如果以后需要树莓派明确显示授权状态，应评审是否利用状态帧保留位或升级协议；不能只改单端字段含义。

## 9. 降落反馈现状

本轮未执行完整航线，也没有发出合法降落请求，因此：

```text
LA=0
LC=0
land_request=false
```

这些结果只能说明“本轮没有进入降落流程”，不能验证：

- 飞控是否会正确接受 `land_request`；
- `land_accepted` 是否按协议返回；
- 真实落地后 `land_completed` 是否能够置位；
- 降落过程中的水平和yaw是否被飞控强制清零。

当前协议文档注明第一阶段 `land_completed` 可能尚未实现。正式实飞前需要飞控端明确其实现状态，并先进行无桨或固定机架的降落状态机测试。

## 10. 树莓派定位侧观察（与飞控串口问题分开）

本轮 Cartographer 能持续输出位姿并驱动PID。启动后机体短暂静止时，位姿约稳定在厘米级；操作者开始手持移动后，坐标和yaw出现明显变化。由于移动范围受线缆限制，无法完成1 m测试航线。

Cartographer 日志中存在较多激光时间戳警告：

```text
Dropped earlier points：699次日志记录
previous subdivision time...：18次日志记录
```

这是雷达驱动/扫描时间顺序与SLAM的独立问题，不应归因于飞控高度传感器或飞控串口。它可能影响水平定位质量，后续需要树莓派侧单独处理。

一次测试中用户界面曾提示 Cartographer “意外关闭”。已保存日志显示本轮 Cartographer 主进程一直运行到收到我们主动发出的 SIGINT；因此目前没有确认到飞行过程中自主崩溃。本轮雷达驱动在主动 SIGINT 时以 `-2` 退出，属于关闭处理不够干净，不是运行中断链。

## 12. 建议下一轮联合测试的通过标准

在继续保持无桨或电机动力断开的前提下：

1. 飞控同时打印原始接收命令、最终执行命令、`RX_SEQ`、`ACK_SEQ`、flags和命令年龄；
2. 连续运行至少10分钟，ACK拒绝应接近0；启动/重连时也不应出现大批旧ACK；
3. 树莓派发送的 mm/s、mrad/s、mm 与飞控换算后的 cm/s、deg/s、cm逐项一致；
4. 遥控器授权关闭时，飞控应在200 ms内把最终执行量清零；
5. 遥控器授权恢复后，只有 `control_valid=true` 才允许应用树莓派控制量；
6. 手持改变高度，记录 `C`、`T`、`HR`、状态帧原始flags，并验证进入容差、退出容差和连续确认时间；
7. 验证 XCOM 的 `HR` 与状态帧 bit0 每次完全一致；
8. 模拟一次合法降落请求，验证 `LA`、`LC` 和降落期间水平/yaw清零；
9. 树莓派侧另做完全静止的定位测试，避免把手持运动误判为SLAM漂移。

满足以上条件后，再进入低高度、短距离、随时可人工接管的首次有动力测试。
