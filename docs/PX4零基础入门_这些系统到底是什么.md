# 零基础入门：这套系统里到底有哪些东西

**读这份文档的前提假设**：你会用电脑、会 SSH、知道文件是什么；但你不知道飞控是什么、不知道 PX4 是什么、不知道 ROS，电子也只懂"正负极"。

全文没有一处需要你先背下英文缩写才能读懂。每个术语**第一次出现时**都用大白话解释一遍，之后就可以放心用。

## 0. 一张全景图

一架"能自己飞的无人机"，内部其实是**两个人**在配合：

| 角色 | 是谁 | 干什么 | 特点 |
| --- | --- | --- | --- |
| **小脑 / 脊髓** | 飞控板（你手上那块 MicoAir H743） | 读传感器、保持平衡、控制四个电机的转速 | 反应极快（**每秒算 1000 次**），但很笨 |
| **大脑** | 树莓派 5 | 认路、画地图、收发电台数据、做决定 | 很聪明，但反应慢（**每秒算几十次**），而且会走神 |

它们之间用**两根线**连起来（一根发、一根收），大脑告诉小脑"往哪飞"，小脑负责"真的飞起来"。

```
                    ┌─────────────────────────────┐
   雷达 ──USB──────►│                             │
                    │        树莓派 5             │   ← 大脑：Linux / 认路 / 画地图 / 通信
   电台 ──串口─────►│   （跑 Ubuntu + 我们的程序） │
                    └──────────┬──────────────────┘
                               │ 两根线（串口）+ 一根地线
                    ┌──────────▼──────────────────┐
   遥控器 ──SBUS───►│       飞控板（H743）        │   ← 小脑：平衡 / 控制电机
                    │   （跑 PX4 固件）            │
                    └──────────┬──────────────────┘
                               │ 四路 PWM 信号
                    ┌──────────▼──────────────────┐
                    │  四个电调 → 四个电机        │   ← 肌肉
                    └─────────────────────────────┘
```

**你现在的进度**：小脑已经会用（M0 已完成：飞控能飞、遥控能切模式）；大脑和小脑之间的那两根线还没接上（M1 要做的）；肌肉（电调+电机）还没到货，所以暂时不能真的转桨。

## 1. 为什么一架无人机里要塞两台电脑？

这是整个方案里最核心的"为什么"，理解了它，后面所有设计都是它的推论。

**因为两种需求是互相打架的：**

- 飞控的工作是"保持平衡"。四个电机转速每变一点，机身的姿态立刻跟着变，姿态变了又要立刻修正。这个循环必须**每秒跑 1000 次**，而且**每一次都必须准时**——晚个几毫秒，飞机就开始抖，晚多了就翻。
- 树莓派的工作是"认路"。它要处理雷达每秒几万个点、跑建图算法、跑网络通信。这些活儿计算量大，偶尔慢个几十毫秒完全无所谓。

于是问题来了：树莓派跑的是 **Linux**。Linux 是个"公平"的系统——它会把 CPU 时间切来切去，保证每个程序都能轮上。这对你的电脑是优点，对"每 1 毫秒必须准时"的任务是致命伤：**你永远无法保证你的程序下一毫秒一定被运行**。

> ### 关键概念：实时 ≠ 快
>
> "实时"这个词很容易被误解。它**不是**指"算得快"，而是指"**绝不迟到**"。
>
> 一个每秒能算一百万次、但偶尔会迟到 20 毫秒的程序，是**非实时**的。
> 一个每秒只算 1000 次、但每次都精准卡在 1 毫秒上下的程序，是**实时**的。
>
> 飞控要的是后者。树莓派天生给不了。这就是为什么要分成两台。

**所以分工是：**
- 树莓派负责"慢而聪明"的部分——认路、决定去哪。
- 飞控负责"快而准"的部分——把"去哪"变成四个电机各自该转多快。
- 树莓派**永远不去直接控制电机**。它只发"目标"，怎么实现是飞控的事。

## 2. "飞控"到底是什么

### 2.1 硬件层

你手上那块板子（MicoAir H743 v2.1.1）上，最核心的是一颗叫 **STM32H743** 的芯片。

- 它是一颗 **单片机**（英文缩写 MCU）。单片机的意思是"一颗芯片里就有 CPU、内存、和各种输入输出接口"，它**不跑操作系统**——你写的程序直接就是这台机器上唯一的程序。
- 正因为没有操作系统来"分心"，它才能做到上面说的"绝不迟到"。
- 板子上还焊了一堆**传感器**：
  - **加速度计 + 陀螺仪**（合称 IMU）：感知"我在往哪边倒、转得多快"。这是飞控最重要的传感器，你的板子上有两个（BMI088 和 BMI270），互相备份。
  - **气压计**：通过空气压力推算高度。精度一般（几米级），但不会突然失效。
  - **磁力计**：感知"哪边是北"，相当于电子罗盘。
  - 板子边缘那些一排一排的插针，是给外部设备的接口，叫 **UART / 串口**（后面详讲）。

### 2.2 软件层：什么是"固件"

- **固件（firmware）**：烧录在硬件里、开机就跑的程序。介于"硬件"和"软件"之间，所以叫固件。你的路由器、电视遥控器里都有固件。
- **PX4** 就是一套飞控固件。**它不是操作系统**，它是一个程序，跑在单片机裸机上。

> **这里要纠正一个常见误解。** 你说同伴好像在"地瓜派上装了个 PX4 操作系统"——PX4 不是操作系统，也没有"装在 Linux 电脑上"这个常规用法。
> 他很可能做的是下面两种之一：
> 1. 在 Linux 上跑 **SITL**（软件在环仿真）——纯粹是把 PX4 当成一个普通程序跑起来，用来在电脑上"假装有一架飞机"，方便调试，**不是真飞**。
> 2. 在 Linux 上直接跑 PX4 当飞控（"PX4 on Linux"）——这需要专门的硬件扩展板（比如 Navio2、PilotPi）来接电机和传感器，而且因为 Linux 不是实时系统，效果不如专用飞控板。
>
> **你的路线是第三种，也是最标准的**：飞控板跑 PX4 固件，树莓派跑 Linux 当"伴飞电脑"。这条路你手上的硬件已经具备。

### 2.3 PX4 内部在忙什么

PX4 是一个"一开机就同时跑几十个小程序"的大程序。每个小程序管一件事，比如：

| 小程序名 | 管什么 |
| --- | --- |
| `sensors` | 从芯片里读传感器原始数据 |
| `ekf2` | 把一堆不准的传感器**融合**成一个"我在哪、朝哪"的估计（见第 7 节） |
| `commander` | 总调度 + 安全守门员：判断"现在允不允许解锁""允不允许进这个模式" |
| `mc_pos_control` | 位置控制：我要去 (x, y, z)，该往哪边加速 |
| `mc_att_control` | 姿态控制：机身该倾斜多少度 |
| `mc_rate_control` | 角速度控制：每秒转多少度 |
| `control_allocator` | 把上面算出来的"总推力 + 三个方向的力矩"**分配给四个电机** |
| `uxrce_dds_client` | 和树莓派通信的"快递员"（见第 6 节） |

这些小程序之间不能互相直接调用，它们靠**发消息**交流。PX4 内部这套消息系统叫 **uORB**——你可以理解成公司内部的**公告板**：谁有消息就贴上去，谁关心就自己去听。

`mc_*` 是 **m**ulti**c**opter（多旋翼）的缩写。你的飞机是四旋翼，所以关心这些。

## 3. "树莓派"是什么

**树莓派就是一台完整的电脑**，只是很小。它有 CPU、内存、存储卡、USB 口、网口、Wi-Fi、蓝牙，跑的是一套和你的笔记本几乎一样的 **Linux**（你的这套装的是 **Ubuntu**，Linux 的一个流行版本）。

区别在于：树莓派的 CPU 是 ARM 架构（省电、便宜），而且它的输入输出引脚可以直接插线控制外部设备。

**在这一套系统里，树莓派扮演的角色叫"伴飞电脑"**（英文 companion computer，"伴飞"就是"陪着飞机一起飞"）。它负责那些飞控干不了的活：

- 处理激光雷达的原始数据
- 跑建图定位算法（SLAM）
- 通过电台和地面站通信
- 跑摄像头做视觉
- **决定"下一步往哪飞"，然后告诉飞控**

> **名词：ROS 2**
> ROS 2 是树莓派上的一套"程序之间互相传消息"的框架。全名 Robot Operating System，但它**不是操作系统**（又一次命名误导），它是一层**胶水**。
> 有了它，你写 20 个各自干一件事的小程序，它们之间靠"发消息"配合，比写一个一万行的大程序清爽得多。
> 你树莓派上装的 `/opt/ros/jazzy`，`jazzy` 是 ROS 2 的一个版本代号（每个版本用一个字母排序的动物/词命名，Jazzy 对应 Ubuntu 24.04）。
>
> **名词：话题（topic）**
> ROS 2 里，消息不发给"某个程序"，而是发到某个**话题**上。话题就像一个广播频道，比如频道名叫 `/scan`，雷达往上发，谁想听谁就订阅。
> - **发布（publish）**：往频道里说话。
> - **订阅（subscribe）**：听这个频道。
> 发的人不需要知道谁在听，听的人不需要知道谁在发——这就是它好用的地方。
>
> **★ 这里有个关键设计**：PX4 也用了同一套思路，并且规定死了频道名字的前缀：
> - 以 `/fmu/out/` 开头的话题 = **飞控 → 树莓派**（飞控"说出"来的，out）
> - 以 `/fmu/in/` 开头的话题 = **树莓派 → 飞控**（树莓派"说进去"的，in）
> `fmu` 是 **F**light **M**anagement **U**nit（飞行管理单元）的缩写，就是"飞控"的另一种叫法。
> **记住这一条，PX4 就懂一半了。** 而且它只有固定的一批名字可用（叫"白名单"），你随便编一个名字是**不会报错但完全没有用**的。

## 4. 两台电脑之间那两根线

这一节是电子初学者最容易翻车的地方，请慢读。

### 4.1 为什么用"串口"

**串口**（英文 UART）是最古老、最简单的数字通信方式：

- 两根信号线：一根叫 **TX**（transmit，发送），一根叫 **RX**（receive，接收）。
- 数据在线上**一位一位地**传：先传高电平还是低电平，按约定好的速度一位一位地读出来。
- 所以必须**交叉连接**：A 的 TX 接 B 的 RX，B 的 TX 接 A 的 RX。**TX 接 TX 是收不到任何数据的**——这是新手第一大坑。

**为什么不用 USB？** 飞控板上确实有一个 USB 口，但那个口的用途是：接电脑用地面站软件（QGroundControl）配置参数、或者刷固件。它不适合当"长期挂着一个树莓派"的通信口。

飞控上真正给外部设备用的，是板子边缘那一排排小插针，标着 **TELEM1 / TELEM2 / GPS / RC** 等，它们就是串口。

### 4.2 波特率：两边必须说一样快

- **波特率**就是"每秒传多少位"，比如 57600 表示每秒 57600 位。
- 两边必须**完全一致**。不一致的结果不是"慢一点"，而是**全是乱码**——就像一个人用两倍速说话，另一个人按正常速听，听到的只是一串噪音。
- 常见值：57600、115200、230400、921600。数字越大越快。

> **★ 这是 M1 最容易漏、也最难查的一件事。**
> 飞控出厂时，串口的波特率默认一般只有 57600；而树莓派那边我们会设成 921600。
> 两边不一致的表现是：**线接对了、程序也起来了，但一个话题都收不到，而且不报任何错**。
> 所以要显式地把飞控侧对应串口的波特率也改成 921600。

### 4.3 共地：为什么必须有第三根线

- "电压"这个词本身没有意义，必须问"**相对谁**"。我们说某根线是 3.3 伏，意思是"它比某个参考点高 3.3 伏"，那个参考点叫 **GND（地）**。
- 如果飞控和树莓派各用各的"地"，两边的"3.3 伏"就是两个不同的标准，读出来全是垃圾。
- 所以除了 TX/RX 两根信号线，**必须再连一根地线**把两边的参考点接在一起。这叫**共地**。

### 4.4 电平与"USB 转串口"

- 飞控的串口引脚是 **3.3 伏**逻辑电平（小电压信号，只能近距离、板对板）。
- 树莓派的 USB 口是 USB 协议（完全不同的电气标准和数据格式）。
- 所以中间需要一个小板子翻译，叫 **USB 转串口模块**。你用的那个芯片是 **CH340**（一种很便宜的国产转换芯片）。
- 完整链路是：

```
飞控 TELEM2 排针  ──TX/RX/GND 三根杜邦线──►  CH340 模块  ──USB 线──►  树莓派 USB 口
```

> **你树莓派上那条 udev 规则就是在给这个模块起固定名字。**
> Linux 给 USB 设备起名字是按"插上的顺序"来的（`/dev/ttyUSB0`、`/dev/ttyUSB1`……），今天插上是 0，明天可能变 1，程序就会找错设备。
> 所以你之前比赛时写了一条规则，让系统认准"CH340 插在那个固定的物理 USB 口上"时，就额外起一个名字 `/dev/flight_controller`。程序里写死这个名字，就不会错。
> **代价**：因为它靠的是"物理位置"，所以**必须插回原来那一个 USB 口**，换口这个名字就不出现了。（CH340 芯片本身没有唯一序列号，所以只能靠物理位置认。）

### 4.5 电从哪来

- **电池**：你的机型用 2~6 节锂电池串联。一节标称 3.7 伏，"6S"就是 6 节，约 22.2 伏。
- **BEC**：飞控板上有个降压电路，把电池的高压降到 **5 伏**，用来给飞控自己和一些外设供电。这个 5 伏输出**最大只能给 3 安培**。
- **★ 树莓派 5 不能吃这个 5 伏。** 树莓派 5 官方要求 5 伏 5 安培（约 27 瓦），3 安培不够，会不稳定甚至反复重启。**树莓派必须自己单独供电**（USB-C 电源或者独立的降压模块）。

### 4.6 电调（ESC）和 PWM

- **PWM**（脉冲宽度调制）：用"高电平占多长时间的比例"来表示一个数值。航模里约定：每 20 毫秒发一个脉冲，脉冲宽度 1000 微秒表示"最小"，2000 微秒表示"最大"。飞控就是用这种方式告诉电调"油门开多大"。
- **电调**（ESC，电子调速器）：无刷电机不能像灯泡一样直接接电，必须靠电调把直流电变成**三相交变电流**，并按顺序切换，电机才会转。电调接收飞控的 PWM 信号，负责驱动电机。
- **所以"电调没到"意味着什么**：飞控可以把"我想让一号电机转 30%"这个意图算出来、并以 PWM 信号的形式输出到引脚上，但**没有电调，这个信号没有任何东西可以驱动**。所以电机相关的验证必须等电调到货。
  - 好消息：**飞控有没有正确算出 PWM，是可以不接电调就检查的**——用地面站软件看它内部输出的数值即可。

### 4.7 你现在的硬件清单状态

| 部件 | 状态 |
| --- | --- |

## 5. 那些名词到底是"东西"还是"软件"

初学最容易混乱的是：一堆名字里，哪些是硬件、哪些是程序、哪些是数据格式。这里一次说清。

| 名字 | 它到底是什么 | 一句话作用 |
| --- | --- | --- |
| **PX4** | 跑在飞控板上的**固件**（程序） | 让飞机能稳定地飞 |
| **uORB** | PX4 **内部**的消息系统 | 飞控各部门之间的公告板 |
| **MAVLink** | 一种**数据格式**（约定怎么打包消息） | 飞控和地面站（QGroundControl）之间的"电话语言" |
| **QGroundControl** | 电脑上的**软件** | 给飞控改参数、看状态、刷固件、看地图 |
| **uXRCE-DDS** | 一套**协议 + 一个程序** | 让树莓派能像读本地消息一样，读写 PX4 内部的 uORB 公告板 |
| **Micro XRCE-DDS Agent** | 跑在**树莓派上的那个程序** | 就是上面那套协议在树莓派这一侧的"翻译 + 快递员" |
| **ROS 2** | 跑在树莓派上的**框架/胶水** | 让你的一堆小程序靠话题互相通信 |
| **`px4_msgs`** | 一个**代码包** | 里面是"PX4 那些消息用 C++ 怎么表示"的定义，写程序时要用 |
| **Cartographer** | 一个**程序**（谷歌开源） | 用雷达数据建地图并定位（SLAM 的一种实现） |
| **EKF2** | PX4 内部的一个**模块** | 把多个不准的传感器融合成"我在哪、朝哪" |
| **offboard** | 飞控的一个**飞行模式** | "控制权交给外部电脑"的模式 |
| **话题 / topic** | 一个**通信频道名** | 消息按名字广播 |
| **QoS** | 一组**传输要求** | 这个频道"丢了要不要重发、要不要留存"的约定 |

**"中间件"这个词**：uXRCE-DDS 这类"负责让两个不同世界的程序互相说话"的东西，统称中间件。它就是"翻译 + 快递"。

## 6. 树莓派和飞控具体怎么对话

回到第 3 节结尾说的：PX4 把话题分成 `/fmu/in/*`（进去）和 `/fmu/out/*`（出来）。但这中间还差一环——

**PX4 内部说的是 uORB，树莓派说的是 ROS 2，两边说的不是同一种话。**

所以要有个翻译，这就是 **uXRCE-DDS** 干的事。完整链路：

```
树莓派上的一个 ROS 2 程序
   │  发布到话题 /fmu/in/trajectory_setpoint
   ▼
Micro XRCE-DDS Agent（树莓派上的翻译程序）
   │  把这消息按 XRCE-DDS 协议打包
   ▼
串口（那两根线，921600 波特率）
   ▼
飞控里的 uxrce_dds_client（PX4 自带的翻译模块）
   │  解包，写进 uORB 公告板，话题名 vehicle_trajectory_setpoint
   ▼
PX4 各部门（commander / mc_pos_control / ...）照常处理
```

**三个必须知道的现实约束：**

1. **版本必须配对。** PX4 1.17 的翻译模块用的是 XRCE **2.x** 版协议，而 Micro XRCE-DDS Agent 最新是 **3.x**，**两者不兼容**。装错版本的现象是："连上了，但一个话题都建不出来"。所以要装 **v2.4.3**。
2. **只有白名单里的话题能用。** PX4 源码里有一张固定清单，只有清单上的名字才真的能通。你随便编一个名字，**不报错，但完全没用**——这是排查时最容易白费半天的地方。
3. **QoS 必须对上。** 这是最阴的一个坑。PX4 和 ROS 2 对"消息该怎么传"的默认要求不一样。ROS 2 默认要求"可靠传输"（丢了要重发），但 PX4 是用"尽力而为"（丢了就丢了）发的。**要求不一样，两边就配不上，结果是：`ros2 topic list` 里根本看不到这个话题**，而且**没有任何错误提示**。

> 顺带一个好消息：你树莓派上**现在还没装**这个翻译程序（我们检查过：`MicroXRCEAgent` 不存在）。M1 的第一件事就是装它。

## 7. "定位"这件事的术语

飞控要控制飞机，首先得**知道自己在哪**。这一块术语最密，但逻辑其实很清晰。

### 7.1 传感器的局限

| 传感器 | 擅长 | 不擅长 |
| --- | --- | --- |
| 加速度计 + 陀螺仪（IMU） | 短时间内的变化，极其灵敏 | 长时间会累积漂移，**单独用几分钟就飘得没边** |
| 气压计 | 高度（大气压随高度变化） | 精度差（几米），天气变化会影响 |
| 磁力计 | 方向（哪边是北） | 附近有电流/铁磁物就被干扰 |
| GPS | 绝对位置 | **室内完全没有信号** |

### 7.2 融合：EKF2

既然每个传感器都不完美，就把它们**合起来用**：IMU 提供短期精度，气压计/GPS/光流提供长期基准，互相纠偏。干这件事的算法叫**卡尔曼滤波**，PX4 里的实现叫 **EKF2**。

> **这就是室内飞行的核心难点**：你把 GPS（唯一的绝对位置来源）拿掉了，就必须再补一个"能给出绝对位置"的来源，EKF2 否则只能靠 IMU 漂。补的来源通常有两种：
> - **光流 + 测距**：朝下的小摄像头测"地面往哪边移动"（=我的速度），朝下的激光测"离地多高"。两个一合，就能算出水平位置。这是室内定点的经典方案。
> - **外部视觉/雷达定位**：用雷达建图定位（SLAM），直接算出"我在房间里的坐标"，然后告诉飞控。**这就是你要走的路。**

### 7.3 定位相关的名词

| 名词 | 大白话 |
| --- | --- |
| **里程计（odometry）** | "相对出发点，我移动了多少" |
| **SLAM** | **S**imultaneous **L**ocalization **A**nd **M**apping：一边画地图、一边确定自己在地图里的位置 |
| **Cartographer** | 谷歌开源的一个 SLAM 程序，你树莓派上用的是它 |
| **坐标系** | 描述位置之前必须先约定"原点在哪、x 朝哪、y 朝哪" |
| **TF** | ROS 2 里的"坐标系登记处"：记录各种坐标系之间怎么换算 |
| **ENU** | 一种坐标系约定：**E**ast 东 = x，**N**orth 北 = y，**U**p 上 = z |
| **NED** | 另一种约定：**N**orth 北 = x，**E**ast 东 = y，**D**own 下 = z |
| **FLU** | 机体系：**F**orward 前 = x，**L**eft 左 = y，**U**p 上 = z |
| **FRD** | 机体系：**F**orward 前 = x，**R**ight 右 = y，**D**own 下 = z |

> **★ 为什么这一块值得单独拿出来强调：** ROS 2 那套（雷达、Cartographer、你以前写的代码）习惯用 **ENU + FLU**；PX4 用的是 **NED + FRD**。
> 两边的 **z 轴方向是相反的**（一个朝上、一个朝下），y 轴也是相反的（左 vs 右）。
> 如果换算写错，结果不是"误差大一点"，而是**前后左右上下全部反了**——飞机朝你希望的反方向猛冲。这是这类项目里炸机的头号原因。
> 所以我们在代码里把换算**集中在一个文件**（`px4_offboard/frame_transforms.cpp`），并且专门写了测试来卡死它。**这是 v2.0.0 那一版唯一做的事。**

## 8. 一条指令的完整旅程

现在把上面所有东西串起来。假设树莓派决定"以 1 米/秒向前飞"，看看会发生什么：

| 步 | 在哪发生 | 做什么 |
| --- | --- | --- |
| 1 | 树莓派 | 某个程序往话题 `/fmu/in/trajectory_setpoint` 发一条消息：速度 = (1, 0, 0) |
| 2 | 树莓派 | Micro XRCE-DDS Agent 把这个消息按协议打包 |
| 3 | 那两根线 | 一位一位地传过去（921600 波特率） |
| 4 | 飞控 | `uxrce_dds_client` 解包，写进 uORB 公告板 |
| 5 | 飞控 | **`commander` 检查"准不准许"**：现在是不是 offboard 模式？有没有位置估计？心跳还在不在？**任何一条不满足就静默丢弃——不报错、不回应** |
| 6 | 飞控 | `mc_pos_control` 想："要往前 1 米/秒，但我现在静止，需要先加速"，算出期望的姿态角 |
| 7 | 飞控 | `mc_att_control` 想："要倾斜 8 度，我现在是 0 度，需要施加多少力矩" |
| 8 | 飞控 | `mc_rate_control` **每秒 1000 次**微调角速度 |
| 9 | 飞控 | `control_allocator` 把"总推力 + 三个方向的力矩"拆成四个电机各自的目标转速 → 输出四路 PWM |
| 10 | 硬件 | 电调收到 PWM → 驱动电机 → 飞机真的往前飞 |

**第 5 步是整条链路上最需要敬畏的一步。** 它意味着：**你可以发得完全正确，但飞控静默地不理你。** 遇到"发了没反应"，九成问题出在第 5 步的准入条件上，而不是第 1~4 步的通信。

## 9. "offboard 模式"到底特殊在哪

平时飞控的控制权在谁手里？在**遥控器**手里（你推杆，它就动）。**offboard** 就是：把控制权交给树莓派。

这是一个**危险**的操作——想象你的电脑忽然获得了控制一架几公斤重飞行器的权限。所以 PX4 给它加了一堆门槛：

| 门槛 | 具体是什么 | 为什么 |
| --- | --- | --- |
| **心跳** | 树莓派必须**持续每秒至少发 2 次**"我还活着"的信号 | 万一树莓派卡死/死机，飞控得知道 |
| **连续喂够 1 秒** | 只发几次不算，必须连续发满 1 秒以上才肯进 offboard | 防止误触发 |
| **必须有位置估计** | 飞控得知道自己在哪 | 否则"去 (1,0,0)"这个目标毫无意义 |
| **断流即退出** | 心跳断了超过 `COM_OF_LOSS_T`（默认 1 秒），自动退出并降级到安全模式 | 保命 |
| **打杆夺不回** | ★ 默认情况下，进了 offboard 后你推遥控器摇杆**没有任何反应** | 这是一个出厂的保守设定，但对我们很危险——**首飞前必须显式打开"打杆夺回控制权"** |

**理解这五条，就理解了为什么我们的实施顺序是这样的**：必须先让飞控知道"它在哪"（否则进不了 offboard），才能谈发指令。这个先后顺序是 PX4 规定的，不能调换。

## 10. 我们的方案，用大白话再说一遍

现在回头看"我们要做什么"，应该不那么抽象了。

### 10.1 现状

- 小脑（飞控 + PX4）✅ 好用。
- 大脑（树莓派）✅ 有，而且**已经会认路了**——你以前比赛做的雷达驱动、Cartographer 建图定位、坐标输出、PID 控制，这些**全部可以继续用**。
- ❌ 缺的是大脑和小脑之间那条"说话的通路"。

### 10.2 只有两个缺口

| 缺口 | 缺什么 | 对应里程碑 |
| --- | --- | --- |
| **A：上行** | 树莓派得把"我在房间里的坐标"告诉飞控（用的是雷达 SLAM 的结果） | **M3** |
| **B：下行** | 树莓派得把"我要往哪飞"发给飞控 | **M4** |

其他所有工作，都是为这两件事做准备的地基和维护。

### 10.3 旧工程里，保留什么、换掉什么

| 部分 | 处理 | 为什么 |
| --- | --- | --- |
| 雷达驱动（`lslidar_driver` + 配置） | ✅ **保留** | 和飞控无关，能用 |
| 建图定位（`cartographer_config` + 配置） | ✅ **保留** | 这就是"认路"的大脑 |
| 坐标输出（`map_coordinate_provider`） | ✅ **保留** | 输出"我在哪" |
| PID 控制（`position_pid_controller`） | ✅ **保留** | 输出"该往哪飞"的速度 |
| 任务流程（`waypoint_manager`） | ✅ **保留** | 比赛任务的执行逻辑 |
| 摄像头/小车/地面站串口桥 | ✅ **保留** | 和飞控无关 |
| **和飞控说话的那一层**（`flight_controller_bridge`） | ❌ **换掉** | 它是为**凌霄飞控的自定义串口协议**写的（30 字节帧、CRC 校验、115200 波特率、厂家私有的命令码）。PX4 的对话方式完全不同（uXRCE-DDS + offboard），**无法在它上面改**，只能新写一个。 |
| PX4 固件 | ❌ **一字节都不动** | 官方版本已经自带我们需要的一切 |

**所以整套改造的本质是**：把"和飞控说话的那一层"整个换成新的，上面所有东西接同一个接口。就像给一台机器换掉一个零件，而不是把整台机器重做。

> **这一层在电脑里通常叫"抽象层"或"适配层"。** 它的价值是：上面那些程序（PID、任务流程）**不知道也不关心**底下接的是凌霄飞控还是 PX4。它们只管把速度指令发到同一个话题上。这样换飞控时，上层一行都不用改。

### 10.4 那条旧桥，我同意不再保留

你说得对，这里我改一下原计划：

- **顾虑是成立的**：`flight_controller_bridge` 那一整套是为凌霄飞控写的私有协议，留着它一是要跟着编译、二是两套并存在 launch 里容易互相干扰、三是以后排查问题时容易把它的残留当成新问题。
- **新决定**：把它从 `src/` 里移出去（移到 `archive/` 目录，不参与编译、不接进启动流程），让 PX4 成为**唯一**的飞控通路。这样就没有"两套并存"的隐形风险。
- **不会丢**：git 历史里有完整记录，`git checkout v1.2.0` 就能把它完整取回来。这也是为什么要坚持每个版本打 tag。

## 11. 里程碑的白话版

| 代号 | 一句话 | 为什么是这个顺序 | 需要硬件吗 |
| --- | --- | --- | --- |
| **M0** | 飞控本身能用 | ✅ **已完成**（能飞、遥控能切模式） | — |
| **M1** | 树莓派能**听**到飞控说话 | 连"读"都不会，谈不上"写"。纯软件+一根线，零风险 | 只需要一根线 |
| **M2** | 树莓派能**给飞控下命令**（但不上锁、不飞） | 先确认"说得进去"，用"请求解锁"这种可观察的命令来验证 | 不需要 |
| **M3** | 飞控知道"自己在哪"（雷达定位结果送进去） | **PX4 规定：没有位置估计就不让进 offboard**。这是最高风险的一步 | 不需要（手持测试） |
| **M4** | 完整跑通"树莓派说往哪飞，飞机就往哪飞" | 前三个都通了才轮到这一步。**必须拆桨** | ✅ 需要电调 |
| **M5** | 室内定点悬停稳住 | 从"能动"到"能稳"，靠调参数 | ✅ 需要电调 |
| **M6** | 接入比赛任务逻辑 | 最后接上层 | ✅ 需要电调 |

**关键点：M1、M2、M3 全都不需要电调到货。** 你现在就可以开始，而且这三步恰好是整个项目里最难、最容易出问题、最值得先做掉的。

## 12. 现在你可以先不管的术语

学习新领域时，最大的负担是"不知道哪些可以先跳过"。下面这些现在**你完全不用管**，用到时再说：

`MAVLink 消息 ID`、`CRC16-CCITT`、`QoS 的 durability/reliability/history 具体枚举`、`POSE_FRAME_FRD`、`nav_state 编号`、`COM_* 参数族`、`MPC_* 参数族`、`EKF2_* 参数族`、`SER_*_BAUD`、`colcon`、`ament_cmake`、`package.xml`、`udev`、`systemd`、`DDS 域 ID`、`话题白名单的具体条目`……

这些都已经写进了另外两份文档，**它们是"手册"不是"教材"**——不需要通读，遇到具体问题时按关键词去查：

- `docs/PX4伴飞工程计划书.md`：决策与施工计划（为什么这么定、下一步做什么）
- `docs/PX4树莓派伴飞实战路线.md`：参数、命令、硬件坑的查询手册
- `docs/M1_操作手册_派能读飞控.md`：M1 阶段照着敲的逐步操作

**你现在唯一需要记住的三件事：**

1. **飞控负责快和准，树莓派负责聪明。** 树莓派永远不直接控制电机，它只说"我要去哪"。
2. **`/fmu/in/*` 是树莓派说给飞控，`/fmu/out/*` 是飞控说给树莓派。**
3. **飞控收到指令后还会做一堆安全检查，不满足就静默丢弃、不报错。** 所以"发了没反应"先怀疑准入条件，不要先怀疑线。
