# 三条通信协议设计 v1（树莓派 ↔ K230 / 小车 / 飞控）

> 状态：**设计稿，待队友确认后冻结为 v1.0**
> 适用版本：`v3.0.0` 起的 G 题工程
> 原则：**三条链路共用一个帧封装**，只有 `TYPE` 和载荷不同。这样解析器写一次、三处复用，
> 抓包工具也只写一次。

## 0. 为什么要有这份文档

三条链路、三个对端（K230 / ESP32-S3 小车 / PX4 飞控），如果没有一份共同遵守的字节级约定，
最后一定是「我以为是这个顺序、他以为是那个顺序」，然后在比赛现场查不出来。

本文档把所有**字节级细节**固定下来：帧头、长度、CRC、字段顺序、单位、频率、超时行为。

## 1. 通用帧格式

三条链路**完全相同**的封装（飞控那条是 MAVLink，不适用本节，见 §5）：

```
偏移  长度  字段      说明
 0     2    SOF      固定 0xAA 0x55
 2     1    VER      协议版本，当前 1
 3     1    TYPE     消息类型（见各链路消息表）
 4     2    LEN      载荷长度（字节），小端
 6   LEN    PAYLOAD  载荷
6+LEN   2    CRC16    CRC-16/CCITT-FALSE，小端，覆盖 VER..PAYLOAD（**不含 SOF**）
```

- **字节序**：全部小端（little-endian）。
- **CRC 参数**：多项式 `0x1021`，初值 `0xFFFF`，不反转，不异或输出。
  与旧串口 V2 协议用的算法一致，代码可直接复用。
- **最大载荷**：64 字节（超过视为非法帧，丢弃并重新同步）。
- **重新同步**：解析器在字节流里搜索 `0xAA 0x55`；LEN 或 CRC 不合理时，**从下一个字节重新搜索**，
  不要整段丢弃 —— 串口/TCP 都可能丢字节。

### 校验用的参考向量（已用代码验证）

```
VER=1  TYPE=0x81  LEN=0x000C  PAYLOAD=00 × 12
CRC-16/CCITT-FALSE(VER..PAYLOAD) = 0x2E0E
整帧 hex = AA 55 01 81 0C 00 00 00 00 00 00 00 00 00 00 00 00 00 0E 2E
```

实现时**先跑一遍 `tools/proto_selftest.py`**，它会把上面这行打印出来并与自身实现比对；
21 项检查全绿（编码→解析往返、粘包、3 字节分片、坏 CRC 丢弃、垃圾前缀重同步、超长载荷拒绝），
才可以拿去接硬件。

### 关于「心跳」

每条链路两端都各自发心跳（`TYPE=0x00`，载荷为空）。收到心跳 = 对端活着。
**超过 1 秒没收到任何帧 ⇒ 判定该链路断开**，按 §4 的故障处理执行。

## 2. 链路 A：树莓派 ↔ K230（下视相机）

### 硬件与参数

| 项 | 值 | 说明 |
|---|---|---|
| 物理层 | UART，**TTL 3.3V** | K230 是 3.3V 电平，**不要接 5V** |
| 接线 | Pi TX→K230 RX，Pi RX→K230 TX，**GND 必须共地** | 交叉接 |
| 波特率 | **115200**，8N1，无流控 | 30 Hz × 约 30 字节 ≈ 1 KB/s，115200 绰绰有余 |
| 角色 | **K230 周期性主动上报，Pi 只在状态变化时下发指令** | 避免两边同时抢发 |

**两阶段接入**（线路随时可能换，所以设备名必须是参数，不能写死）：

| 阶段 | 接法 | Pi 侧设备 | 备注 |
|---|---|---|---|
| **现在** | 排线直连树莓派 GPIO UART | `/dev/ttyAMA0`（或 `/dev/serial0`） | 现有工程就是这么接的 |
| **目标** | CH340 USB-TTL 转接 | **`/dev/k230`**（udev 固定名，见 §9） | 换线不用改代码 |

★ **`k230_bridge` 的设备名必须是 launch 参数**，默认 `/dev/k230`；
接 GPIO 时传 `serial_device:=/dev/ttyAMA0` 即可，**代码一行不改**。


### 坐标系与单位（★ 最容易错的地方）

K230 给出的偏移是**地面平面上的偏离长度，单位 cm**，定义为：

```
off_x_cm : 目标点相对「相机正下方地面点」在机体前向的偏移
           正 = 目标在机头前方，负 = 在机尾方向
off_y_cm : 同上，机体左向
           正 = 目标在机体左侧，负 = 右侧
```

**这与 ROS 2 的 FLU 约定一致（x 前 / y 左）。**
Pi 收到后直接用来算速度设定点：`v_cmd = k × off`，`k` 由 `k230_bridge` 参数给。
**不要**在 K230 侧做符号翻转 —— 全工程统一 FLU，只在 `px4_offboard` 一处转 NED/FRD。

> 高度换算谁做？占用 `height_cm` 字段：K230 把自己的安装高度（或它用来换算的假设高度）
> 一并报上来，Pi 侧就能判断这个 cm 值是不是可信（高度变了就得重新标定比例）。

### Pi → K230（TYPE 0x01 ~ 0x0F）

| TYPE | 名称 | 载荷 | 频率 |
|---|---|---|---|
| `0x00` | HEARTBEAT | 空 | 5 Hz |
| `0x01` | CMD_MODE | `mode(u8)` | 状态变化时 |
| `0x02` | CMD_SET_ROI | `x0(u16) y0(u16) x1(u16) y1(u16)` 像素，用于限制检测区域 | 可选 |
| `0x03` | **CMD_SET_HEIGHT** | `height_cm(i16) valid(u8)` | **10 Hz** |

#### `0x03 CMD_SET_HEIGHT`（★ 让 cm 偏移随高度实时换算）

K230 把像素偏差换成地面 cm 偏移，公式是 `off_cm = (px − cx) × height / f`（`f` 为像素焦距）。
**高度错了，cm 就整体缩放错。**

以前凌霄飞控不给高度，K230 只能用**一个固定高度**；现在树莓派能从飞控拿到高度
（`LOCAL_POSITION_NED.z` 或 EKF 的 `dist_bottom`），所以改成**实时下发**：

```
 0   2  height_cm  i16   相机到地面的距离，cm
 2   1  valid      u8    bit0=高度可信 bit1=使用测距(而非气压/推算)
 3   1  reserved   u8    填 0
```

K230 的行为：
- `valid & 1` ⇒ 用这个高度实时换算，并把它回显到 `VISION_STATE.height_cm`
- `valid` 为 0 或超过 500 ms 没收到本帧 ⇒ **退回参数里的固定高度**，并在 `flags` 置 `HEIGHT_FIXED`

Pi 侧发什么高度：
- 首选飞控的 `dist_bottom`（EKF 融合测距，最接近「离地距离」）
- 退而求其次 `LOCAL_POSITION_NED.z` 取负（相对起飞点的高度）
- **两者都失效时发 `valid=0`**，让 K230 用固定值，而不是发一个错的高度


`CMD_MODE.mode` 取值：

| 值 | 名称 | 含义 |
|---|---|---|
| 0 | `STANDBY` | 待机，只回心跳，不做检测 |
| 1 | `SEARCH` | 巡逻扫描：检测红点，报像素与 cm 偏移，不做伺服 |
| 2 | `ALIGN` | 视觉伺服：报更细的 cm 偏移 + 是否对准标志 |
| 3 | `STOP` | 立即停止一切输出（急停） |

### K230 → Pi（TYPE 0x81 ~ 0x8F）

| TYPE | 名称 | 载荷 | 频率 |
|---|---|---|---|
| `0x00` | HEARTBEAT | 空 | 1 Hz |
| `0x81` | **VISION_STATE** | 见下 | **30 Hz** |
| `0x82` | EVENT | `event(u8) ts_ms(u32)` | 事件触发 |
| `0x83` | STATUS | `fps(u8) cpu(u8) ts_ms(u32)` | 1 Hz |

#### `0x81 VISION_STATE` 载荷（共 20 字节）

```
偏移 长度 字段         类型      说明
 0    1   found        u8        1=画面里有红点，0=没有
 1    1   mode         u8        回显当前模式（0..3）
 2    2   px           u16       红点像素 x（画面左上为原点）
 4    2   py           u16       红点像素 y
 6    2   off_x_cm     i16       机体前向偏移，cm，正=前方
 8    2   off_y_cm     i16       机体左向偏移，cm，正=左侧
10    2   height_cm    i16       换算时使用的高度，cm
12    2   flags        u16       见下
14    2   quality      u16       置信度 0..1000（0=最差，1000=最好）
16    4   ts_ms        u32       K230 侧毫秒时间戳（回绕无所谓，只用于算新鲜度）
```

`flags` 位定义：

| 位 | 名称 | 含义 |
|---|---|---|
| bit0 | `ALIGNED` | 已对准：`|off_x_cm|` 与 `|off_y_cm|` 均小于 K230 侧阈值 |
| bit1 | `LOST` | 曾经锁定、现在丢了（用于区分「从没看到」和「看到又丢了」） |
| bit2 | `READY_DROP` | 满足投放条件（对准 + 高度合适），Pi 可以投 |
| bit3 | `LOW_LIGHT` | 环境光不足，检测可能不可靠 |
| bit4 | `SATURATED` | 红点过曝/面积过大，偏移不可信 |
| **bit5** | **`HEIGHT_FIXED`** | **当前用的是参数里的固定高度，不是实时高度 —— cm 偏移的缩放可能不准** |
| **bit6** | **`OVER_RATE`** | **本帧是降频运行的（实际帧率低于目标 30 Hz）** |
| bit7-15 | 保留 | 必须填 0 |

> `HEIGHT_FIXED` 与 `OVER_RATE` 是两个「不致命但要记下来」的降级位。
> Pi 侧收到 `HEIGHT_FIXED` 时，视觉伺服的增益应自动调小（比例错了，增益不能再大）。


#### `0x82 EVENT.event` 取值

| 值 | 名称 | 何时发 |
|---|---|---|
| 1 | `TARGET_ACQUIRED` | 首次稳定锁定 |
| 2 | `TARGET_LOST` | 连续丢失超过 N 帧 |
| 3 | `ALIGN_DONE` | 进入 `ALIGN` 模式后首次满足对准 |
| 4 | `ERROR` | 内部错误（如相机初始化失败） |

### 故障处理

| 情况 | Pi 侧动作 |
|---|---|
| 1 秒无任何帧 | 判链路断开：`/k230/online = false`，任务层进入 `HOLD`，**不继续投放** |
| `found=0` 且 `LOST` 置位 | 任务层进入搜索/回航线 |
| `quality < 300` 连续 10 帧 | 视为不可信，忽略该目标 |
| `SATURATED` 置位 | 忽略本帧偏移，只用 `found` |

## 3. 链路 B：树莓派 ↔ 消防车（`pos_link`，TCP over WiFi）

> **本节已按实际实现重写（2026-11-27）。** 早前设计过一套 9000 端口、`AA 55 + VER + TYPE + LEN`
> 变长帧的 `car_link` 包，**该包与 `tools/car_link_sim.py` 已删除**。
> 以后小车的通信**只在 `src/comm/pos_link` 上改**，不再并行维护第二套协议。
> 原设计的多字段想法压缩保存在本节末尾「附：候选扩展字段（未实现）」。

### 实现现状

| 项 | 值 |
|---|---|
| 包 | `src/comm/pos_link`（`ament_python`） |
| 物理层 | WiFi 2.4GHz；树莓派 `wlan0` 开热点当 AP（SSID `PiLink`，网段 `192.168.50.1/24`） |
| 角色 | 树莓派 **TCP Server**，监听 `0.0.0.0:5000`；ESP32-S3 **TCP Client**，主动连上来 |
| 帧 | **12 字节定长**，小端 |
| 方向 | **树莓派 → ESP32，单向**（ESP32 不回包） |
| 频率 | 1 Hz（`send_period_ms=1000`） |
| 已验证 | 真机联调通过；离线校验 10/10（参考帧逐字节吻合、坏帧全拒、分片/粘包/重同步） |

### 帧格式（12 字节）

| 偏移 | 长度 | 字段 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 2 | 帧头 | — | `0xAA 0x55` |
| 2 | 1 | TYPE | u8 | 固定 `0x01` = 坐标帧 |
| 3 | 1 | seq | u8 | 0~255 循环，供车侧检测丢帧 |
| 4 | 2 | x | i16 LE | 坐标 x |
| 6 | 2 | y | i16 LE | 坐标 y |
| 8 | 2 | CRC16 | u16 LE | CRC-16/CCITT-FALSE，**覆盖 [0]~[7]** |
| 10 | 2 | 帧尾 | — | `0x0D 0x0A` |

参考帧（`pos_link/frame.py` 的 `build_frame()`、固件 `main.c`、本章**三处是同一份值**）：

```
x=100 y=200 seq=0  →  AA 55 01 00 64 00 C8 00 E5 FC 0D 0A
x=7   y=3   seq=1  →  AA 55 01 01 07 00 03 00 14 5E 0D 0A
```

> ⚠ CRC 算法与 §1 通用帧相同（CRC-16/CCITT-FALSE），但**覆盖范围不同**：
> 本链路固定覆盖前 8 字节，不含 §1 那种 `VER/LEN` 语义。

### 参数（`src/comm/pos_link/config/pos_link.yaml`）

| 参数 | 默认 | 说明 |
|---|---|---|
| `listen_port` | `5000` | 必须与固件 `HOST_PORT` 一致 |
| `input_topic` | `/pos_link/target` | 坐标来源话题（`geometry_msgs/PointStamped`） |
| `send_period_ms` | `1000` | 下发周期（毫秒），最小 50 |
| `hold_last_on_stale` | `true` | 坐标过期后继续发最后一帧（见下方故障处理） |
| `stale_warn_s` | `5.0` | 多久没新坐标算过期 |

> 配置文件的顶层键必须是 **`pos_link_bridge`** —— 代码里节点名定死，写错参数静默不生效。

### 坐标系与单位

**必须用场地坐标**，不是 SLAM 坐标：

```
原点 = 巡防区左下角 (0, 0)
x 轴 = 向右（沿 48dm 方向），单位 cm
y 轴 = 向上（沿 40dm 方向），单位 cm
```

有效范围 `x ∈ [0, 480]`、`y ∈ [0, 400]`。

> 传输用 **cm（int16）** 而不是 dm：赛题显示用 dm，但 dm 粒度 10cm 对「落点半径 3dm」判断太粗。
> 显示层自己除以 10。

★ **现状与待补**：`bridge_node.py` 目前只把值夹到 int16 范围（±32767），
**没有做 `[0,480]×[0,400]` 的场地范围校验** —— 上游算错就会把越界坐标原样发出去。
待补：参数化 `x_min/x_max/y_min/y_max`，越界**丢弃并告警**（不要夹，夹等于悄悄改了目标）。

### 怎么扩展（要加字段 / 加消息 / 双向时）

1. **加字段**：`frame.py` 的 `FRAME_LEN`、固件 `main.c` 的 `read_frame()`、本章三处一起改，
   测试里的参考帧同步更新。
2. **加消息类型**：帧头 `0xAA 0x55` 与帧尾 `0x0D 0x0A` **保持不变**，用第 3 字节区分
   （现在是 `TYPE_POS=0x01`；火源坐标可用 `0x02`、航程 `0x03`）。
   要变长就学 §1 在 seq 后面加 `LEN` —— 但**不要换帧头**，换了等于两套解析器。
3. **要双向**：ESP32 → 树莓派用同一套帧、TYPE 取 `0x81+`，在 `bridge_node.py` 的
   `_accept_loop()` 里读回包。

### 故障处理

| 情况 | 现在的行为 | 建议 |
|---|---|---|
| 坐标源 5 s 无更新 | `hold_last_on_stale=true`：继续发最后一帧并告警 | 若担心车「一直朝旧目标走」，改 `false`，或要求车侧 2 s 无帧停车 |
| 车断开 | 打印 `累计断开 N 次`，等它重连 | 重连由 ESP32 侧负责 |
| 坐标越界 | **目前不拦**（只夹 int16） | 按上文补范围校验 |
| Pi 侧 `connect()`（其实是 accept）异常 | 打印告警并继续监听 | — |

### 附：候选扩展字段（未实现，原 `car_link` 设计，将来并回本链路时参考）

- `z_cm`（离地高度）、`heading_d10`（航向 ×10 度，0..3599）、`valid` 位图（位置有效/高度有效/正在飞/任务进行中）
- `FIRE_REPORT`：`fire_id(u8 1..3) + x_cm(i16) + y_cm(i16) + ts_ms(u32)`
- `MILEAGE`：`total_cm(i32) + delta_cm(i32) + ts_ms(u32)`
- `MISSION_STATE`：`state(u8)`，取值 `IDLE/TAKEOFF/PATROL/APPROACH/ALIGN/DROP/RETURN/LAND/DONE/ABORT = 0..9`
- 上行（车 → Pi）：`CAR_STATUS`、`FIRE_EXTINGUISHED`、`ACK`

> 这些字段一旦要用，就按上面「怎么扩展」加进 `pos_link`，**不要再开第二个包**。

## 4. 统一的故障与降级策略

| 链路 | 断开判据 | 断开后 |
|---|---|---|
| A（K230） | 1 s 无帧 | 停止视觉相关阶段 → `HOLD` 悬停，等重连或超时后回航线 |
| B（小车 / `pos_link`） | TCP 连接断开，或坐标源 5 s 无更新 | 无人机**继续执行当前任务**（赛题要求全程无干预）；`hold_last_on_stale=true` 时继续发最后一帧，否则停发；车侧应在 2 s 无帧时自行停车 |
| C（飞控） | 0.5 s 无心跳 / offboard 断流 | PX4 自己触发 failsafe（`COM_OF_LOSS_T`），我们只负责**不停发**设定点 |

★ 铁律：**任何一条链路断开，都不能让飞机失去控制。** 飞控侧永远保留遥控器模式开关作为兜底。

## 5. 链路 C：树莓派 ↔ 飞控（MAVLink）

这条**不是自定义协议**，直接用 MAVLink v1（`MAV_PROTO_VER=1`，因为 MTF-01 光流要求）。

我们只需要固定「用哪些消息、什么频率、什么语义」：

### 上行（Pi → FC）

| MAVLink 消息 | ID | 频率 | 用途 |
|---|---|---|---|
| `VISION_POSITION_ESTIMATE` | 102 | 30–50 Hz | 雷达 SLAM 位姿 → EKF2（`EKF2_EV_CTRL=1` 只融水平位置） |
| `SET_POSITION_TARGET_LOCAL_NED` | 84 | 10–20 Hz | 速度设定点（offboard 核心） |
| `COMMAND_LONG` | 76 | 事件 | `DO_SET_MODE`(176) 切 offboard、`COMPONENT_ARM_DISARM`(400) 解锁/上锁 |
| `REQUEST_MESSAGE` | 512 | 按需 | 向上拉特定消息 |
| `PARAM_SET` / `PARAM_REQUEST_READ` | 23 / 20 | 调试 | 改/读参数 |

★ **offboard 心跳**：MAVLink 路线下没有 `OffboardControlMode` 这条消息，
**设定点流本身就是心跳** —— 只要 `SET_POSITION_TARGET_LOCAL_NED` 以 ≥2 Hz 持续发送，
PX4 就认为 offboard 存活。**停发即退出 offboard**。

### 下行（FC → Pi）

| MAVLink 消息 | ID | 轮询频率 | 用途 |
|---|---|---|---|
| `LOCAL_POSITION_NED` | 32 | **25 Hz** | 位置/速度/航向（实测可达 24.6 Hz） |
| `ATTITUDE` | 30 | 30 Hz | 姿态（四元数/欧拉） |
| `ESTIMATOR_STATUS` | 230 | 2 Hz | `pos_horiz_ratio` / `pos_vert_ratio` 判断 EKF 融合质量 |
| `EXTENDED_SYS_STATE` | 245 | 2 Hz | `landed_state`（判断是否真正离地/落地） |
| `HEARTBEAT` | 0 | 2 Hz | `base_mode` / `custom_mode`（当前飞行模式、是否 armed） |
| `COMMAND_ACK` | 77 | 事件 | 确认模式切换/解锁是否成功 |

★ **为什么是轮询而不是 `SET_MESSAGE_INTERVAL`**：实测本机固件对 `MAV_CMD_SET_MESSAGE_INTERVAL(244)`
回 `UNSUPPORTED`，而对 `MAV_CMD_REQUEST_MESSAGE(512)` 回 `ACCEPTED` 且工作良好。
按需轮询的总流量实测 **6.5 KB/s**（下行 4.2 + 上行 2.4），对 11.5 KB/s 的线路很宽裕。

### 与 ROS 2 话题的映射

| ROS 2 话题 | 方向 | MAVLink |
|---|---|---|
| `/map/current_pose` | 订阅 | → `VISION_POSITION_ESTIMATE` |
| `/pid/cmd_vel` | 订阅 | → `SET_POSITION_TARGET_LOCAL_NED`（速度） |
| `/flight/status` | 发布 | ← `HEARTBEAT` + `LOCAL_POSITION_NED` + `ESTIMATOR_STATUS` |
| `/flight/command` | 订阅 | → `COMMAND_LONG` |

坐标系换算**只在 `px4_offboard/src/frame_transforms.cpp` 一处**：
位置 `(y, x, −z)`、姿态两次四元数积、机体速度 `(vx, −vy, −vz)`、偏航 `π/2 − yaw`。

## 7. 待确认（冻结 v1.0 前必须定）

| # | 问题 | 状态 / 结论 |
|---|---|---|
| Q1 | K230 用 USB-TTL 还是 GPIO UART 接？ | **✅ 已定**：现在走 GPIO UART，之后改 CH340 USB。故设备名做成参数，默认 `/dev/k230`，接 GPIO 时传 `/dev/ttyAMA0` |
| Q2 | K230 的 cm 偏移是否随高度重算 | **✅ 已定**：以前固定高度（凌霄飞控不给高度）；现在改为 **Pi 以 10 Hz 下发 `CMD_SET_HEIGHT`**，K230 实时换算并回显；失效时退回固定高度并置 `HEIGHT_FIXED` |
| Q3 | K230 能否稳定 30 Hz | **⚠ 未测**。历史比赛表现「很快」，但没有实测数字。故协议带 `OVER_RATE` 位，且 `k230_bridge` 的输出频率做成参数；**第一次接上就要实测**，低于 15 Hz 则视觉伺服改为「走走停停」而非连续修正 |
| Q4 | 小车 TCP 端口 | **✅ 已定**：**5000**（`pos_link`，固件 `HOST_PORT` 与之对应），参数可改。小车侧代码由你自己写（先在自己板上验证再迁到队友板） |
| Q5 | 小车是否需要航迹原始点序列 | 待定 —— 建议先只发实时点，车侧自己画曲线并累加航程（数据量最小） |
| Q6 | `fire_id` 由什么决定（评委点亮顺序？场上位置？） | 待现场确认 |
| Q7 | 投放机构怎么下发（GPIO / PWM / 独立单片机） | 待定 |

### 关于 30 Hz 的实测方法（Q3）

接上之后在树莓派上跑：

```bash
python3 tools/k230_rate_probe.py --dev /dev/k230 --seconds 10
```

它只解析 `VISION_STATE` 帧、统计实际帧率、抖动（相邻帧间隔的 p95）与丢帧位置。
判据：**平均 ≥20 Hz 且 p95 间隔 <80 ms** ⇒ 可以做连续视觉伺服；否则改用「到位→停→再测」的间歇策略。

## 8. 落地顺序

1. ✅ 写 `tools/proto_selftest.py`：三条链路的帧编解码 + CRC 自检（33 项全绿，CRC 参考向量 `0x2E0E`）
2. `k230_bridge`（链路 A）→ `/k230/vision_state`、`/k230/online`
3. ✅ `pos_link`（链路 B，**已跑通**）→ TCP `:5000` 下发 12 字节坐标帧；坐标源经 `/pos_link/target` 注入
4. ✅ `px4_offboard`（链路 C，只读阶段已完成）→ `/flight/status`；上行骨架已就位（`enable_uplink`，默认关闭）
5. 三条链路都通了，再写 `competition_g` 任务状态机把它们串起来

> **先自测编解码、再接硬件**，是因为协议错一次会浪费半天在「是协议错还是硬件坏」上。

## 9. 两个 CH340 的坑（必读）

改用 USB-CH340 接 K230 后，树莓派上会同时插着**两个一模一样的 CH340**：

| 设备 | USB 芯片 | VID:PID | 序列号 |
|---|---|---|---|
| 飞控 | CH340 | `1a86:7523` | **无**（读出来是空） |
| K230 | CH340 | `1a86:7523` | **无** |

两者 VID/PID 完全相同、都没有序列号 ⇒ **只能用「插在哪个 USB 口」来区分**。
现有的飞控规则就是这么写的（注释原文：*The CH340 has no unique serial number, so the physical path is required.*）。

### udev 规则模板

```udev
# 飞控（已存在）
SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="7523", \
  ENV{ID_PATH}=="platform-xhci-hcd.1-usb-0:1:1.0", \
  SYMLINK+="flight_controller", GROUP="dialout", MODE="0660"

# K230 —— ID_PATH 必须换成 K230 实际插的那个口
SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="7523", \
  ENV{ID_PATH}=="platform-xhci-hcd.1-usb-0:2:1.0", \
  SYMLINK+="k230", GROUP="dialout", MODE="0660"
```

查实际 `ID_PATH`：

```bash
udevadm info -q property -n /dev/ttyUSB1 | grep -E 'ID_PATH|ID_SERIAL'
```

### ★ 由此产生的三个操作纪律

1. **两条 CH340 线必须贴标签**（飞控 / K230），并且**永远插回固定的那两个口**。
   插反了不会报错，只会让 `/dev/flight_controller` 和 `/dev/k230` **互换** ——
   飞控数据被当成视觉帧解析，画面是「一堆 CRC 错」，极难查。

2. **不要用 USB Hub。** Hub 的 `ID_PATH` 会多一层（`…-0:1.2:1.0`），改一次 Hub 插口规则就失效。

3. **上电后先确认这两个软链指向的设备在不在**：

   ```bash
   ls -l /dev/flight_controller /dev/k230
   ```

   任何一个不存在，先解决接线，再谈代码。

### 一个「插反了」的自检办法

两个设备的波特率与数据特征完全不同：

| 设备 | 空闲时线上有什么 |
|---|---|
| 飞控 | 若无 MAVLink 请求，基本静默；有请求时是 MAVLink 帧（`0xFE` / `0xFD` 开头） |
| K230 | 跑起来就持续 30 Hz 发 `AA 55 01 81 …` |

所以：**用 `tools/k230_rate_probe.py --dev /dev/flight_controller` 探一下**，
如果收到的是 `AA 55` 帧，说明插反了。反之亦然。
